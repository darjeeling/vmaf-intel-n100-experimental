# Intel N100 VMAF v2 성능 테스트 목록

2026-09-27 기준 [Netflix/vmaf](https://github.com/Netflix/vmaf)의 **열린 이슈 75개와 열린 PR 64개 전부**의 제목과 본문을 읽고 추렸다. 목록은 이후 변경될 수 있다. PR에 적힌 타 장비의 커널 성능 수치는 N100의 FFmpeg 전체 처리 성능으로 환산하지 않는다.

현재 비교 대상은 VMAF v1 모델의 CAMBI, chroma SpEED, integer ADM, integer Motion이다. Intel N100은 AVX2와 Intel 내장 GPU를 사용한다. 지금까지 가장 빠른 조합은 GPU VAAPI 디코딩과 직접 매핑, CPU feature 계산이며, Q22 300프레임에서 설치 바이너리 8.354초 대비 실험 바이너리 5.786초(전체 시간 30.7% 감소)였다. OpenCL Motion/ADM 계산은 이 조합보다 느렸다. 아래 후보는 이 기준 위에서 **각각 추가 효과가 있는지** 검증한다.

검증은 현재 실험 바이너리와 동일한 모델·옵션·입력으로 한다. 각 후보는 같은 빌드 기준에서 **단독 A/B**, Q20/Q22/Q24 300프레임 반복 실행, 전편 확인 순서로 진행한다. 중앙값과 처리율을 함께 기록하고, frame별 feature·pooled 점수를 비교한다. ADM 변경은 기존 영상 외에 고대비·작은 프레임·폭이 SIMD 블록의 배수가 아닌 입력도 포함한다. 장시간 실행은 [이슈 #1394](https://github.com/Netflix/vmaf/issues/1394)의 처리율 저하 주장도 확인하도록 구간별 속도와 메모리를 기록한다. 반복마다 캐시·CPU 온도·클럭·GPU 사용률을 기록해 단순 변동과 구분한다.

[PR #1598](https://github.com/Netflix/vmaf/pull/1598)의 checkasm 기준 브랜치 비교 방식은 위 SIMD 후보의 마이크로벤치에 참고할 수 있다. checkasm 향상만으로 채택하지 않고 FFmpeg 프로세스 전체 시간을 최종 기준으로 삼는다. 정확도 게이트에는 [이슈 #972](https://github.com/Netflix/vmaf/issues/972)의 picture 수명 경쟁, [이슈 #910](https://github.com/Netflix/vmaf/issues/910)의 Motion flush, [이슈 #1400](https://github.com/Netflix/vmaf/issues/1400)의 마지막 프레임 누락도 포함한다.

현재 모델에 없는 VIF의 [PR #1585](https://github.com/Netflix/vmaf/pull/1585)(PR의 17%는 VIF 커널 측정)와 [이슈 #940](https://github.com/Netflix/vmaf/issues/940)은 **VIF 모델을 별도로 운영할 때만** 테스트한다. CUDA 전용 PR, Python/FIFO 경로, 모델 자체를 바꾸는 제안, 기능 추가·문서·CI·정확도 전용 항목은 현재 N100 v1 성능 후보에서 제외했다. 열린 항목 전체를 검토했지만 위 순위는 현재 모델과 실행 경로에 실제로 닿는 항목만 대상으로 한다.

## v2 실행 결과

기존의 빠른 FFmpeg 경로(VAAPI 디코딩·직접 매핑·picture import·SpEED selected-row 계산)를 고정하고 libvmaf만 교체했다. [PR #1602](https://github.com/Netflix/vmaf/pull/1602)를 공통 정확도 기반으로 적용한 다음 [#1586](https://github.com/Netflix/vmaf/pull/1586), [#1609](https://github.com/Netflix/vmaf/pull/1609), [#1584](https://github.com/Netflix/vmaf/pull/1584)를 각각 단독으로 빌드·시험했다. 세 성능 변경의 결합은 코드 충돌을 수동으로 해소한 별도 빌드이며, 최종 후보의 단위 테스트는 22/22 통과했다. 저장소의 일반 소스와 설치 바이너리는 변경하지 않았다.

아래의 입력 A와 B는 각각 1920×1080 8-bit 영상이다. A는 약 24fps, B는 약 60fps 원본을 사용한다. 영상 이름과 파일명은 기록하지 않는다. 벽시계 시간은 디코딩, feature 계산, JSON 기록과 종료를 포함한다. 점수 차이 0은 **기록된 JSON 정밀도** 기준이다.

### 두 CPU 제한 재측정

FFmpeg 프로세스 전체를 CPU 0·1에 고정하고 VMAF `n_threads=2`, 두 입력의 디코더 각각 `-threads 1`, filter complex 1스레드로 설정했다. 프로세스 affinity가 실제 `0,1`인지 확인했다. 기존 빠른 빌드와 v2에 동일한 설정을 사용했고, 300프레임은 실행 순서를 교차해 각 5회 측정했다. GPU는 VAAPI 디코딩에 사용하고 feature 계산은 CPU에서 수행했다.

| 두 CPU 제한 | 기존 빠른 빌드 | v2 결합 | 시간 감소 | 기록된 점수 차이 |
|---|---:|---:|---:|---:|
| 입력 A, 300프레임 5회 중앙값 | 9.901초 / 30.30fps | 9.354초 / 32.07fps | **5.53%** | 0 |
| 입력 B, 300프레임 5회 중앙값 | 9.914초 / 30.26fps | 9.359초 / 32.05fps | **5.59%** | 0 |
| 입력 A, 전편 5,921프레임 각 1회 | 188.48초 / 31.41fps | 178.20초 / 33.23fps | **5.45%** | 0 |
| 입력 B, 전편 11,574프레임 각 1회 | 371.06초 / 31.19fps | 349.02초 / 33.16fps | **5.94%** | 0 |

두 CPU 제한에서는 두 입력의 전편과 300프레임 반복 측정이 모두 같은 방향이었다. 전편은 각 1회이므로 이 5.45~5.94%를 다른 호스트 부하 조건까지 보장하는 값으로 보지 않는다. 기록된 모든 frame별 metric 및 pooled metric은 두 전편에서 일치했고 picture 복사·fallback은 0이었다.

처음의 **설치된 FFmpeg와 v2를 직접 비교**할 때도 같은 두 CPU affinity, VMAF 2스레드, 입력별 디코더 1스레드를 적용했다. 설치본은 기존 10-bit 전처리 경로, v2는 위 8-bit 최적화 경로다. 각 입력 300프레임을 5회씩 교차 실행한 중앙값이다.

| 설치본 대비 전체 개선 | 설치본 | v2 | 처리 시간 감소 | 처리율 증가 |
|---|---:|---:|---:|---:|
| 입력 A | 14.179초 / 21.16fps | 9.405초 / 31.90fps | **33.67%** | **50.76%** |
| 입력 B | 13.977초 / 21.46fps | 9.303초 / 32.25fps | **33.44%** | **50.24%** |

두 입력 모두 기록된 metric 차이는 0이었다. 이 수치는 전체 처리 경로의 직접 비교 결과이며, 앞서 측정한 최적화별 개선율을 더해서 만든 값이 아니다.

### 앞선 4스레드 측정과 변동

| 300프레임, 각 3회 중앙값 | 기존 빠른 빌드 | v2 결합 | 시간 감소 | 기록된 점수 차이 |
|---|---:|---:|---:|---:|
| 입력 A, 중간 구간 | 5.792초 / 51.79fps | 5.548초 / 54.07fps | 4.21% | 0 |
| 입력 B, 중간 구간 | 5.791초 / 51.80fps | 5.541초 / 54.15fps | 4.32% | 0 |
| 입력 B, 시작 구간 | 5.645초 / 53.15fps | 5.399초 / 55.56fps | 4.35% | 0 |

입력 B의 후반 300프레임에서도 점수는 일치했지만, 실행 도중 기존 빌드 한 회차가 5.84초에서 7초대로 변했다. 이 구간에서 계산된 22.6% 개선율은 호스트 경합의 영향을 받아 성능 근거로 사용하지 않는다. 단독 후보 중 #1584는 두 입력 중간 구간의 3회 중앙값에서 약 3.2~3.4% 단축했다. #1586·#1609 단독 및 둘의 결합은 한 회씩 선별 측정했으며, 반복 확인 없이 추가 효과를 단정하지 않는다.

| 전편, 각 1회 실행 | 기존 빠른 빌드 | v2 결합 | 시간 변화 | 기록된 점수 차이 |
|---|---:|---:|---:|---:|
| 입력 A, 5,921프레임 | 107.89초 / 54.88fps | 102.30초 / 57.88fps | 5.19% 단축 | 0 |
| 입력 B, 11,574프레임, 기존→v2 순서 | 235.25초 / 49.20fps | 251.60초 / 46.00fps | 6.95% 증가 | 0 |
| 입력 B, 11,574프레임, v2→기존 순서 | 260.39초 / 44.45fps | 255.59초 / 45.28fps | 1.84% 단축 | 0 |

입력 B의 전편 결과는 실행 순서를 바꾸자 방향이 뒤집혔다. 기존 빌드 자체가 235.25초와 260.39초로 크게 달라졌으므로, 이 장비의 현재 백그라운드 부하에서는 **전편 성능 우위를 확정하지 않는다**. 다만 두 전편의 모든 frame별 metric과 pooled metric은 기존 빠른 빌드와 일치했고, 각각 11,842개와 23,148개 picture가 복사 없이 import됐다. GPU는 VAAPI 디코딩에 사용했고 feature 계산은 CPU에서 수행했다.

최종 후보는 로컬 `build/n100/v2-test/ffmpeg-v2` 실행 스크립트와 전용 libvmaf 공유 라이브러리로 보존했다. 결합 소스는 `tools/experimental/n100/v2-adm-combined.patch`에 보존했고 현재 저장소에 대한 `git apply --check`를 통과했다. 실행 파일과 라이브러리는 로컬 빌드에 의존하며 저장소에 포함되지 않는다. 이번 두 CPU 제한 재측정은 동일 장비에서 v2의 전편 개선을 확인했지만, 동시 작업과 호스트 부하가 다른 상황까지 일반화하지 않는다.
